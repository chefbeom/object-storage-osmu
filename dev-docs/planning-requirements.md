# OSMU 기획 요구사항

이 문서는 OSMU가 최종적으로 어떤 제품이 되어야 하는지, 사용자가 목표로 한 방향을 기준으로 정리한 기획 요구사항 문서이다.

상세 PRD는 `PRODUCT_REQUIREMENTS.md`를 기준으로 하고, 장기 목표는 `PROJECT_MEMORY.md`를 기준으로 한다. 이 문서는 두 문서 사이에서 제품 방향과 요구사항을 개발 가능한 형태로 좁히는 역할을 한다.

## 1. 제품 목표

OSMU의 목표는 기업이 자체 인프라에서 대용량 파일을 안전하게 저장, 관리, 공유, 재사용할 수 있는 B2B 프라이빗 오브젝트 스토리지 플랫폼을 만드는 것이다.

완성된 제품은 특정 기업 내부 전용 시스템이 아니라, 여러 기업 환경에 설치해 사용할 수 있어야 한다.

### 1.1 핵심 목표

- AWS S3 같은 외부 클라우드 스토리지 의존도를 낮춘다.
- 기업 내부에 S3 호환 오브젝트 스토리지를 구축한다.
- 영상, 이미지, 비디오, 문서, 로그, AI 학습 데이터 등 다양한 파일을 저장한다.
- REST API와 S3 호환 API를 모두 제공한다.
- Web Portal로 관리자와 사용자가 스토리지를 관리할 수 있게 한다.
- 중앙 집중식 권한, 사용량, 버킷, 백업, 감사 로그 관리를 제공한다.
- 설치형 B2B 제품으로 확장 가능한 구조를 만든다.

### 1.2 제품 한 줄 정의

기업이 자체 인프라에서 주요 S3 클라이언트로 대체 사용할 수 있는 대용량 파일 저장, 관리, 공유, 백업용 프라이빗 오브젝트 스토리지 플랫폼.

## 2. 해결해야 하는 문제

기업은 현재 대용량 데이터를 여러 방식으로 흩어 저장한다.

- AWS S3
- FTP 서버
- NAS
- USB
- 외장 하드디스크
- 개별 서버 디스크
- 부서별 파일 서버
- 서비스별 독립 저장소

이 방식은 다음 문제를 만든다.

### 2.1 통합 스토리지 부재

부서와 서비스마다 저장 위치가 다르면 데이터 공유가 어렵다. 같은 파일이 여러 곳에 중복 저장되고, 관리자는 전체 사용량과 접근 권한을 파악하기 어렵다.

### 2.2 보안 위험

외부 저장소나 물리 저장 장치를 사용하면 데이터 유출, 분실, 권한 회수 실패 위험이 커진다. 민감 데이터는 외부 클라우드에 저장하기 어려운 경우도 있다.

### 2.3 비용 비효율

대용량 영상, 이미지, 학습 데이터는 외부 클라우드에 장기간 저장할수록 비용이 커진다. 다운로드 비용과 API 호출 비용도 누적된다.

### 2.4 운영 복잡성

저장소가 분산되면 백업, 복구, 모니터링, 용량 증설, 장애 대응이 어렵다.

### 2.5 재사용 어려움

데이터가 부서별로 흩어져 있으면 AI 학습, 영상 처리, 분석, 백업, 서비스 재활용에 필요한 데이터 재사용성이 낮아진다.

## 3. 대상 고객

### 3.1 1차 대상

- 자체 대용량 파일 저장소가 필요한 기업
- AWS S3 비용을 줄이고 싶은 기업
- 보안상 외부 클라우드 사용이 어려운 기업
- 영상과 이미지 원본을 대량 저장하는 기업
- AI 학습 데이터를 내부에서 관리해야 하는 기업

### 3.2 확장 대상

- 스트리밍 플랫폼
- 클라우드 스토리지 플랫폼
- 미디어 기업
- 제조/연구/공공기관
- 헬스케어 데이터 보관 조직
- 사내 데이터 플랫폼 운영 조직

## 4. 사용자 유형

### 4.1 시스템 관리자

- 스토리지 상태와 장애 확인
- 백업과 복구 정책 관리

### 4.2 조직 관리자

- 특정 부서 또는 프로젝트 저장소 관리
- 팀 구성원 권한 부여
- 조직별 사용량 확인

### 4.3 일반 사용자

- 파일 업로드, 다운로드, 삭제
- 버킷 조회
- Access Key 확인
- REST API 또는 S3 API 사용

### 4.4 애플리케이션 개발자

- 서비스에서 S3 API 또는 REST API로 파일 저장
- 영상, 이미지, 로그, 백업 파일 업로드
- SDK와 CLI를 이용해 자동화 구성

## 5. 접근 방식 요구사항

OSMU는 하나의 접근 방식만 제공하면 안 된다. 기업 환경마다 사용 방식이 다르므로 여러 접근 방식을 제공해야 한다.

### 5.1 Web Portal

- 관리자와 사용자가 브라우저에서 파일과 버킷을 관리할 수 있어야 한다.
- 관리자 대시보드, 사용자 대시보드가 필요하다.

### 5.2 REST API

- 자체 서비스와 쉽게 연동할 수 있어야 한다.
- 인증, 버킷, 파일, 사용자, 권한, 사용량 API를 제공해야 한다.

### 5.3 S3 호환 API

- AWS SDK, boto3, MinIO Client, AWS CLI 같은 기존 도구의 핵심 bucket/object/multipart 흐름과 호환되어야 한다.
- AWS S3 전체 동작 복제가 아니라, 내부 스토리지 전환에 필요한 대체 가능성을 목표로 한다.
- S3 API의 data plane은 MinIO와 OSMU S3-compatible alias가 함께 담당하고, OSMU는 계정, 권한, 버킷, 메타데이터 관리 기능을 제공한다.

### 5.4 FUSE Mount

- goofys, s3fs-fuse 같은 도구로 파일시스템처럼 마운트할 수 있어야 한다.
- MVP에서는 문서와 설정 가이드부터 제공한다.

### 5.5 CLI

- 초기 MVP 필수는 아니다.
- 장기적으로 관리자와 개발자 자동화를 위해 제공한다.

## 6. MVP 요구사항

MVP는 "기업 내부에 설치해 실제로 파일을 저장하고 관리할 수 있는 최소 제품"을 목표로 한다.

### 6.1 MVP 필수 기능

- MariaDB 기반 메타데이터 저장
- MinIO 기반 오브젝트 저장
- Docker Compose 기반 로컬 실행
- Backend API 서버
- Web Portal
- 로그인
- 사용자 관리
- 버킷 생성, 조회, 삭제
- 파일 업로드, 다운로드, 삭제
- 파일 목록 조회
- Access Key 발급
- 기본 권한 관리
- 기본 사용량 조회
- 기본 감사 로그

### 6.2 MVP 성공 기준

- 로컬 환경에서 MariaDB와 MinIO가 실행된다.
- Backend가 MariaDB에 연결된다.
- Backend가 MinIO에 연결된다.
- 사용자가 로그인할 수 있다.
- 사용자가 버킷을 만들 수 있다.
- 사용자가 파일을 업로드하고 다운로드할 수 있다.
- S3 클라이언트로 파일 업로드와 다운로드가 가능하다.
- Web Portal에서 버킷과 파일을 확인할 수 있다.
- 관리자 또는 사용자가 기본 사용량을 확인할 수 있다.

### 6.3 MVP 제외 범위

- 자체 오브젝트 스토리지 엔진 직접 구현
- 모든 S3 API 직접 구현
- 고급 과금 기능
- 고급 미디어 변환 기능
- CDN 연동
- 완전한 멀티 리전 복제
- 전체 RAID 레벨 직접 구현
- 완전 자동 장애 복구
- SaaS 멀티테넌트 과금 모델

## 7. 기능 요구사항

### 7.1 인증

- 사용자는 로그인할 수 있어야 한다.
- JWT 기반 인증을 제공한다.
- 관리 API는 인증 없이 접근할 수 없어야 한다.
- 비밀번호는 평문으로 저장하지 않는다.

### 7.2 사용자 관리

- 관리자는 사용자를 생성할 수 있어야 한다.
- 관리자는 사용자를 비활성화할 수 있어야 한다.
- 사용자는 자신의 프로필과 사용량을 볼 수 있어야 한다.

### 7.3 조직 관리

- 관리자는 조직 또는 프로젝트를 생성할 수 있어야 한다.
- 사용자는 조직에 소속될 수 있어야 한다.
- 조직별 사용량을 확인할 수 있어야 한다.

### 7.4 버킷 관리

- 사용자는 권한이 있는 버킷 목록을 조회할 수 있어야 한다.
- 사용자는 버킷을 생성할 수 있어야 한다.
- 사용자는 권한이 있는 버킷을 삭제할 수 있어야 한다.
- 버킷 이름은 S3 호환 규칙을 따라야 한다.
- 기본 버킷은 private이어야 한다.

### 7.5 파일 관리

- 사용자는 권한이 있는 버킷에 파일을 업로드할 수 있어야 한다.
- 사용자는 권한이 있는 파일을 다운로드할 수 있어야 한다.
- 사용자는 권한이 있는 파일을 삭제할 수 있어야 한다.
- 파일 확장자는 제한하지 않는다.
- 대용량 파일을 고려해 streaming 또는 multipart upload를 지원해야 한다.

### 7.6 Access Key 관리

- 사용자는 S3 API 접근용 Access Key를 발급받을 수 있어야 한다.
- Secret Key는 생성 시 한 번만 표시한다.
- 사용자는 Access Key를 비활성화할 수 있어야 한다.

### 7.7 권한 관리

- 관리자, 조직 관리자, 일반 사용자 역할을 구분한다.
- 버킷 단위 읽기/쓰기/삭제 권한을 관리한다.
- 권한 변경은 감사 로그에 남긴다.

### 7.8 사용량과 쿼터

- 사용자별 사용량을 조회할 수 있어야 한다.
- 버킷별 사용량을 조회할 수 있어야 한다.
- 사용자 또는 버킷별 기본 용량 제한을 설정할 수 있어야 한다.

### 7.9 감사 로그

다음 작업은 감사 로그에 남긴다.

- 로그인 성공/실패
- 사용자 생성/비활성화
- 버킷 생성/삭제
- 파일 업로드/다운로드/삭제
- Access Key 생성/삭제
- 권한 변경
- 쿼터 변경

### 7.10 모니터링

- 전체 저장 용량을 확인할 수 있어야 한다.
- 사용 중인 용량을 확인할 수 있어야 한다.
- MinIO 상태를 확인할 수 있어야 한다.
- Backend 상태를 확인할 수 있어야 한다.
- 장기적으로 Prometheus와 Grafana를 연동한다.

### 7.11 백업

- MVP에서는 백업 전략과 설정 가이드를 제공한다.
- 장기적으로 외부 S3 호환 저장소, 원격 클러스터, NAS 백업을 지원한다.

## 8. 비기능 요구사항

### 8.1 보안

- 기본 접근 정책은 private이다.
- Secret Key, Password, Token은 로그에 남기지 않는다.
- TLS 적용을 운영 기본값으로 본다.
- 권한 검사는 모든 관리/파일 API에서 수행한다.

### 8.2 확장성

- MinIO 노드와 디스크 확장을 고려한다.
- Backend는 수평 확장 가능한 구조를 목표로 한다.
- 대용량 파일 처리는 Backend 병목을 최소화한다.

### 8.3 안정성

- MinIO의 Erasure Coding 또는 Replication을 활용한다.
- MariaDB는 백업 가능해야 한다.
- 장애 발생 시 원인 추적 가능한 로그를 남긴다.

### 8.4 운영성

- 로컬 개발 환경은 Docker Compose로 실행 가능해야 한다.
- 운영 환경은 Kubernetes와 Helm을 목표로 한다.
- 설정은 환경변수 또는 설정 파일로 분리한다.

### 8.5 호환성

- AWS S3 SDK, boto3, AWS CLI, MinIO Client의 핵심 사용 흐름과 호환되어야 한다.
- s3fs-fuse, goofys 연동은 기본 목표가 아니라, 고객 전환 시나리오가 확인될 때 검증/지원 범위를 넓힌다.
- AWS S3 세부 edge behavior는 지원 클라이언트 smoke 실패나 고객 마이그레이션 영향이 확인될 때만 선별 보강한다.

## 9. 데이터 저장 원칙

- 실제 파일 데이터는 MinIO에 저장한다.
- MariaDB에는 메타데이터와 관리 정보를 저장한다.
- DB에 대용량 파일 바이너리를 저장하지 않는다.
- 파일 메타데이터는 필요한 범위만 DB에 저장한다.

MariaDB 저장 대상:

- 사용자
- 조직
- 버킷 메타데이터
- 권한
- Access Key 메타데이터
- 쿼터
- 감사 로그
- 시스템 설정

MinIO 저장 대상:

- 영상 파일
- 이미지 파일
- 문서 파일
- 로그 파일
- 백업 파일
- AI 학습 데이터
- 기타 모든 오브젝트 데이터

- MinIO 연결 확인 API
- MariaDB 연결 확인
- 버킷 생성/조회/삭제
- 파일 업로드/다운로드/삭제
- 기본 Web Portal

- 기본 사용량 조회

Spring Boot 패키지 구조, 계층 분리, 예외 처리, MinIO Adapter, 인증/권한 구조를 정의한다.

### 11.4 로컬 개발 환경 설계서

Docker Compose, MariaDB, MinIO, 포트, 환경변수, 실행 순서를 정의한다.

### 11.5 Frontend 설계서

## 12. 첫 개발 마일스톤

첫 마일스톤은 "파일을 실제로 저장할 수 있는 최소 흐름"이다.

범위:

1. MariaDB + MinIO 로컬 실행
2. Backend 실행
3. Backend에서 MinIO 연결 확인
4. Bucket API 구현
5. Object API 구현
6. Vue에서 버킷 목록과 파일 목록 확인

완료 기준:

- `docker compose up`으로 MariaDB와 MinIO 실행 가능
- Backend Health API 정상 응답
- MinIO Health API 정상 응답
- REST API로 버킷 생성 가능
- REST API로 파일 업로드 가능
- REST API로 파일 다운로드 가능

## 13. 기획 판단 기준

새 기능을 추가할 때 다음 기준을 확인한다.

- 기업 내부 대용량 파일 저장 문제를 해결하는가?
- S3 대체 또는 보완 제품으로 가치가 있는가?
- 보안, 비용, 공유, 운영 효율 중 하나를 개선하는가?
- 설치형 B2B 제품으로 판매 가능성을 높이는가?
- MVP 완성을 과도하게 늦추지 않는가?

## 14. 결론

OSMU는 단순 파일 업로드 서비스가 아니다.

목표는 기업이 자체 인프라에서 운영할 수 있는 S3 호환 프라이빗 오브젝트 스토리지 플랫폼이다.

초기에는 MariaDB, MinIO, Spring Boot Backend, Vue Web Portal, Docker Compose 기반으로 MVP를 만든다.

이후 Kubernetes, Helm, 백업, 복제, 모니터링, SSO, 권한 고도화, 설치 자동화를 추가해 B2B 판매 가능한 제품으로 확장한다.
